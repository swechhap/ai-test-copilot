# Enterprise and Senior-Practitioner Pain Points with AI-Powered Test Automation (2024-2026)

## What recurring complaints appear in verified reviews (G2/Capterra/TrustRadius), conference talks, blog post-mortems, and HN/Reddit threads about AI test automation tools?

### Takeaway
The most consistent, evidence-backed complaints are: (1) "AI" locators/self-healing are far less intelligent than marketed and frequently require manual fixes anyway; (2) self-healing actively masks real regressions rather than only fixing cosmetic drift; (3) tools are slow, expensive, and hard to scale on large suites; and (4) trust in AI-made changes to test code remains low because the process is opaque ("black box") and probabilistic.

### Cited Findings
- Tricentis Testim reviewers report "AI locators may not be as 'intelligent' as claimed — some elements don't get recognized during automation testing and require manual changes to locators, with locator instability occurring across development branches." — [G2 Tricentis Testim Reviews](https://www.g2.com/products/tricentis-testim/reviews)
- A direct Testim user review states: "The reality is that the tests do not heal themselves under any circumstance." — [G2.com via AI Testing Intelligence substack, 2025](https://aitestingintelligence.substack.com/p/self-healing-tests-the-marketing)
- A Mabl user review states: "The product has more bugs than its worth, and it takes longer to perform its tests." — [G2.com via AI Testing Intelligence substack, 2025](https://aitestingintelligence.substack.com/p/self-healing-tests-the-marketing)
- Mabl reviewers describe cloud execution as slow, setup as "painfully difficult and long," and the product as "a highly priced, overly complicated solution that actually slows teams down." Other complaints: inability to link multiple rows from a data table within a single test case, and cases where Mabl "can't find the field, button, or part of the page that was selected in test creation and simply stops running with no error message." — [G2 mabl Reviews](https://www.g2.com/products/mabl/reviews)
- Katalon TrustRadius reviewers cite "slow Azure integration, non-responsive customer support, and delayed email responses," plus the desktop app using excessive memory even on 16GB RAM machines; the licensed version is said to not provide "adequate support and value for money." — [TrustRadius Katalon Reviews](https://www.trustradius.com/products/katalon/reviews)
- A competitive teardown of common user complaints across 10+ tools found recurring patterns: Katalon — "advanced features are expensive or locked behind paid tiers," performance struggles on large suites, crashes, UI instability; testRigor — slow mobile environment initialization, crashes, reliability/stability problems, "slower performance than marketed"; Applitools — "web interface described as clunky and unintuitive," oversensitivity to minor UI changes causing excessive false alerts, cost cited as a barrier; Testim — debugging requires extra steps, insufficient logging/diagnostics, high pricing, "test flakiness, false positives, and code export friction"; Tosca — steep learning curve, prohibitive licensing costs, inadequate vendor support response times; Testsigma — performance degradation on larger suites, API/migration issues, locator accuracy inconsistencies. — [DEV Community competitive analysis](https://dev.to/xiami9378389/competitive-analysis-of-15-ai-testing-toolspricing-core-features-and-common-user-complaints-5bhh)
- A Hacker News "Ask HN: AI Supported Test Automation?" thread participant noted they had "looked at several vendors but is still not certain of benefits they might provide," and that "the space is crowded with commercials and praises, many appearing to be AI-generated." — [Hacker News](https://news.ycombinator.com/item?id=41981207)
- One HN commenter who had a positive experience still qualified it: tests starting from "intent rather than a script" worked well because the tool "healed steps a renamed button broke" while "still flagging actual product defects" — implying this reliable behavior is the exception commenters felt compelled to call out, not the norm. — [Hacker News](https://news.ycombinator.com/item?id=41981207)
- The Association for Software Testing's monthly newsletter states bluntly: "In practice, the results have been… well… disappointing," and asks "if these AI tools really are magical changing the way we test… who's actually using them?" It further reports that "testers and quality leaders across the globe are pushing back on these claims of AI glory on the regular, asking for nothing more than evidence and demonstrated success cases," and documents a common adoption pattern: "Many companies initially buy into the hype, run small proofs-of-concept without fully committing, and then give up when their testing teams forget about the tool." — [Association for Software Testing Newsletter, Feb 28, 2025](https://associationforsoftwaretesting.substack.com/p/ast-monthly-newsletter)
- Ministry of Testing Club forum members raised: data-privacy blockers — "The product is private and highly sensitive. Nothing can be shared with an AI" (user ipstefan/Stefan Papusoi); skepticism about practical value — "I wonder for what a tester would need a muse / word prediction program" (user sebastian_solidwork/Sebastian Stautz); and concern about training-data quality/bias, i.e., whether AI "respond[s] with the average generic mainstream views because they are in abundance online" rather than expert insight (user andrewkelly2555/Andrew). — [Ministry of Testing Club forum thread](https://club.ministryoftesting.com/t/to-what-extent-do-you-feel-current-ai-software-testing-tools-meet-your-projects-needs/75863)
- Other Ministry of Testing threads surface the probabilistic-output trust problem directly: "AI is a tool with a probabilistic output, how can you trust it to verify the tests if every time it can output different results?" and warn "the danger is when we accept the information blindly when it could be wrong." AI test-case generation tools are also said to show "a strong bias towards known risks" and to emphasize positive scenarios while omitting negative ones. — [Ministry of Testing Club](https://club.ministryoftesting.com/t/ai-discussion-on-tools/74733)

### Inferences
- Across vendor-specific G2/TrustRadius reviews and independent teardown blogs, the complaint pattern is remarkably consistent regardless of vendor (Testim, Mabl, Katalon, testRigor, Applitools, Tosca, Testsigma all show up with overlapping complaints), suggesting these are structural limitations of the current generation of "AI-powered" commercial test tools rather than vendor-specific execution failures.
- The gap between marketing language ("self-healing," "intelligent locators") and practitioner-reported reality (manual fixes still required, false positives, instability) is a recurring theme and should be flagged as a genuine practitioner complaint, not vendor spin — it is vendor claims that practitioners are explicitly refuting in their own reviews.

### Gaps
- Could not locate a large, systematically-sampled set of raw G2/Capterra star ratings broken out by sentiment for 2024-2026; findings rely on aggregator summaries and a handful of directly quoted reviews rather than a full corpus pull (G2/TrustRadius review pages were summarized via search rather than fully scraped).
- No direct Reddit (r/QualityAssurance, r/Playwright, r/softwaretesting, r/devops) threads with practitioner quotes were successfully retrieved; search results surfaced aggregator/blog commentary about such discussions rather than primary thread content. This is a genuine gap — treat Reddit-specific findings as absent, not negative.

## Are there case studies or post-mortems of AI testing tool adoption failing, abandoned, or causing incidents (e.g., self-healing hiding a regression)?

### Takeaway
Yes — multiple independent write-ups document concrete scenarios (and one quantified simulation) where AI self-healing allowed real regressions to pass as green, and practitioners have coined specific failure patterns ("silent coverage erosion," "Silent Healers" vs. "Transparent Healers") to describe this risk; a Capgemini/Sogeti global survey also quantifies the broader pilot-to-production abandonment gap.

### Cited Findings
- A detailed write-up opens with a concrete incident: "A critical user registration bug" where new users "couldn't complete signup if their email contained certain special characters" made it to production and sat undetected for two days because "the self-healing AI tool automatically 'fixed' broken tests," masking the defect. — [AI Testing Intelligence substack: "Self-Healing Tests: The Marketing Lie Breaking Production"](https://aitestingintelligence.substack.com/p/self-healing-tests-the-marketing)
- The same source documents a second scenario: a self-healing tool replaced a specific CSS selector with a loose XPath after a UI update; "three weeks later," the loose selector matched the wrong element, "the test passed incorrectly, and bug made it to production." — [AI Testing Intelligence substack](https://aitestingintelligence.substack.com/p/self-healing-tests-the-marketing)
- A third documented scenario: when authentication flows changed, a self-healing tool "adjusted wait times and loosened assertions," so tests passed "despite legitimate failures in authentication behavior affecting real users." — [AI Testing Intelligence substack](https://aitestingintelligence.substack.com/p/self-healing-tests-the-marketing)
- The author audited "17 tools" and categorized them into three types: "Silent Healers (auto-deploy, dangerous), Loose Healers (imprecise fixes), and Transparent Healers (approval-based, like Playwright's Healer Agent)" — an explicit practitioner taxonomy of risk levels across the current market. — [AI Testing Intelligence substack](https://aitestingintelligence.substack.com/p/self-healing-tests-the-marketing)
- Industry commentator Andrew Whitehouse is quoted articulating the core objection to self-healing as a design philosophy: "Things should only ever fail for the right reasons. I don't want things 'healing', I want them red for the right reasons!" — [AI Testing Intelligence substack](https://aitestingintelligence.substack.com/p/self-healing-tests-the-marketing)
- A governance-focused article aimed at digital banking modeled a 12-month simulation comparing three regimes: static baseline (no self-healing) — 180 maintenance hours/month, failed to detect 12 defects; ungoverned AI self-healing — 99 hours/month (45% reduction in effort) but coverage-erosion incidents rose 4x (from 7 to 28 over the period); governed framework with human oversight — 58 hours/month (68% reduction vs. baseline), 94% false-positive interception rate, only 2 escaped defects and 1 coverage-erosion incident annually. The piece states plainly: "A test failed. No one even realizes it, but thanks to an AI-powered self-healing tool the failed locator is replaced and the pipeline becomes green again." — [SD Times: "The Hidden Risk in Self-Healing Test Automation: A Governance Blueprint for Digital Banking"](https://sdtimes.com/software-testing/the-hidden-risk-in-self-healing-test-automation-a-governance-blueprint-for-digital-banking/)
- A separate critique argues self-healing doesn't fix the underlying problem: "A heal cannot tell a moved button from a broken feature." It identifies four structural issues: (1) cost at scale — "every heal is an inference call" that "scales with UI churn, which is exactly the thing that's increasing"; (2) introduced flakiness — "non-deterministic element matching on low-confidence heals. A guess that passes on one run and picks a different element on the next is a flaky test"; (3) new maintenance burden — "every ElementNotFound now had two possible meanings: the locator drifted, or the feature is broken. Someone had to decide which, for every heal"; (4) doesn't address root cause — "healing moved the breakage from 'fails loudly' to 'gets patched quietly.'" It also argues AI coding agents have made the underlying problem worse: "agents don't preserve your data-testid conventions unless told to," increasing UI churn and making healing "economically unfeasible at scale." — [devassure.io: "Self-Healing Test Automation Treats the Wrong Disease"](https://devassure.io/blog/self-healing-test-automation-problems)
- On adoption abandonment broadly (not self-healing specific): the World Quality Report 2025-26 (Capgemini/Sogeti/OpenText, 2,000+ senior executives across 22 countries/10 sectors) found that while ~90% of organizations are pursuing generative AI in quality engineering, only 15% have achieved enterprise-scale deployment (37% in production, 52% still in pilot). Top barriers cited: integration complexity (64%), data privacy risks (67%), skill gaps (50%), and hallucination/reliability concerns (60%). A third of organizations report only minimal productivity gains despite adoption. — [Capgemini World Quality Report 2025 press release](https://www.capgemini.com/news/press-releases/world-quality-report-2025-ai-adoption-surges-in-quality-engineering-but-enterprise-level-scaling-remains-elusive/)
- Separately, one industry stat cited (secondary source, not independently verified against a primary report) states "88% of agent pilots never graduate to production," with "evaluation gaps cited by 64% of leaders, ahead of governance friction at 57% and model reliability at 51%." Flag: this figure's original primary source was not identified during this research pass; treat as a secondary/aggregated claim pending verification. — [Medium: "AI Testing Adoption Gap: Hype vs Reality in QA (2025-2026)"](https://medium.com/@accounts_89844/ai-testing-adoption-gap-hype-vs-reality-in-qa-2025-2026-qa-engineers-b57f84cb67b3)

### Inferences
- The recurring narrative structure across independent sources (a "heal" silently replacing a broken element/locator, a delay before the real defect surfaces, and discovery only after user-facing impact) suggests this is a recognized and named failure mode in the practitioner community, not a single anecdote — multiple unrelated authors describe functionally identical scenarios using similar language ("silent," "masked," "coverage erosion").
- The 12-month banking simulation (SD Times) is presented as a model/simulation rather than a real disclosed incident at a named bank — it should be cited as an illustrative quantified scenario, not as a confirmed real-world postmortem at a specific regulated institution.

### Gaps
- No named, publicly disclosed enterprise incident (i.e., a specific company admitting "our AI testing tool self-healed over a real production bug and we shipped it") was found. The scenarios above are described as composite/illustrative examples or anonymized "a user" stories in blog posts, not attributed war stories with company names. This is a meaningful gap — the report should note that documented pain points are strong and consistent, but a named public postmortem/incident report from an enterprise was not located in this research pass.
- Could not verify whether any G2/TrustRadius review explicitly describes a self-healing-caused production incident (reviews found describe quality/reliability dissatisfaction generally, not a specific "it hid a regression and we shipped it" narrative with full detail).

## What do test automation thought leaders say publicly are the biggest unsolved problems in AI + test automation?

### Takeaway
Named thought leaders (Paul Grizzaffi, Simon Stewart, Angie Jones) consistently flag the same core issue from different angles: AI-generated/maintained test code is more opaque than traditional automation, doesn't reliably save time once verification is accounted for, and can cause tests to be skipped or defects to be missed due to hallucination — meaning human judgment and skepticism remain essential rather than optional.

### Cited Findings
- Paul Grizzaffi (UT Dallas Advanced Research Center for Software Testing and QA) "believes AI is currently overhyped" and has expressed concern about "the fresh danger that AI can write tests and test code for us," warning that people expecting "one and done" tests that are "resilient, durable, and effective over time" may be surprised. — [TestGuild podcast interviews with Paul Grizzaffi](https://testguild.com/podcast/automation/a444-paul/)
- Grizzaffi reports direct personal experience comparing roll-your-own automation against AI-written test code and found "the time to have vetted and confirmed versions of AI-generated tests versus tests he created himself was roughly equal" — i.e., no net time savings once verification work is included. He also notes AI "is more opaque than 'traditional' automation for testing, raising questions about trust in automated processes." — [TestGuild podcast](https://testguild.com/podcast/159-great-judgement-comes-great-responsibility-paul-grizzaffi/)
- Simon Stewart (longtime Selenium project lead, co-editor of W3C WebDriver/WebDriver BiDi specs) on using AI for test selection/filtering: "AI seems attractive and is an excellent pattern spotter, [but] it hallucinates, and we end up not running tests we should have." — [search aggregation of Simon Stewart talks/podcasts, 2025](https://www.ministryoftesting.com/p/shs96c)
- Angie Jones (Head of Developer Relations, Applitools) states "AI can assist greatly in automation, but it cannot completely solve problems on its own. Human intervention is essential to guide AI and ensure that it performs tasks as intended, rather than relying on it as a catch-all solution." She also flags that the industry conversation is missing how to test AI/ML itself as it becomes embedded in applications, and raises ethics/data-protection concerns specifically for "sensitive fields like healthcare or finance." — [Applitools blog / TestGuild podcast with Angie Jones](https://testguild.com/podcast/194-reality-testing-artificial-world-angie-jones/)

### Inferences
- There is convergence among three independent, credentialed voices (Grizzaffi, Stewart, Jones) on two specific unsolved problems: (1) hallucination/opacity undermines trust and can cause missed defects or skipped tests, and (2) AI does not eliminate the human verification burden — it shifts where the effort goes rather than removing it.

### Gaps
- Could not locate direct public commentary from current Playwright core team members (e.g., Debbie O'Brien, Max Schmitt) specifically critiquing AI testing tool limitations; only third-party references to a Playwright "Healer Agent" as an example of a "Transparent Healer" were found, not direct core-team quotes on unsolved problems.
- No direct, attributable public statement from Microsoft/Google test architects on this topic was found in this research pass.

## What do enterprises cite as blockers to adopting AI testing agents at scale (security/compliance review, cost, reliability, skills gap)?

### Takeaway
The dominant, consistently-cited enterprise blockers are: integration complexity into existing CI/CD and toolchains, data privacy/security review requirements, a persistent skills gap in configuring and governing AI tools, and reliability/hallucination concerns — with governance and audit-trail requirements acting as a distinct, additional blocker in regulated sectors (finance, healthcare, insurance).

### Cited Findings
- World Quality Report 2025-26 (Capgemini/Sogeti/OpenText survey of 2,000+ senior executives, 22 countries, 10 sectors): top barriers to scaling AI in quality engineering are integration complexity (64%), data privacy risks (67%), skill gaps (50%), and hallucination/reliability concerns (60%); 60% of organizations struggle with secure, scalable test data; 58% cite challenges adopting AI-powered tools generally. — [Capgemini WQR 2025 press release](https://www.capgemini.com/news/press-releases/world-quality-report-2025-ai-adoption-surges-in-quality-engineering-but-enterprise-level-scaling-remains-elusive/)
- A secondary aggregator reports "60% of QA teams say they lack sufficient skills to configure and govern AI testing tools effectively, and only 29% have a formal AI-QA strategy as of 2024," and cites Deloitte identifying "the AI skills gap" as "the most commonly cited barrier to deeper integration." Also: "50% report their organizations lack AI/ML expertise, which is unchanged from 2024." — [Medium: AI Testing Adoption Gap aggregation](https://medium.com/@accounts_89844/ai-testing-adoption-gap-hype-vs-reality-in-qa-2025-2026-qa-engineers-b57f84cb67b3) — Flag: this is an aggregator citing Deloitte secondhand; the original Deloitte report was not directly located/verified in this pass.
- Gartner-sourced reporting: "Only 15% of IT leaders are adopting fully autonomous AI agents, as concerns over governance and trust slow enterprise deployment," and "only 19% of respondents reported high or complete trust in their vendor's ability to provide adequate hallucination protection." Gartner also stated that "many AI vendors have yet to demonstrate the stability, governance and continuity traditionally expected of enterprise technology providers," and that "the trust of these vendors is not warranted yet" because they are "not enterprise grade." — [ARN/IDG coverage of Gartner](https://www.arnnet.com.au/article/4221889/ai-vendors-testing-traditional-it-assumptions-and-creating-trust-deficit-gartner.html)
- Gartner also found the primary obstacle to AI adoption overall (49% of survey participants) is "difficulty in estimating and demonstrating the value of AI projects" — ranked above talent shortages, technical difficulties, data issues, business alignment, and trust. — [Gartner coverage via CIO Dive / search aggregation](https://www.ciodive.com/news/generative-ai-adoption-barrier-project-value/716504/)
- On governance/audit trail specifically for regulated industries: a compliance-focused piece states requirements include that "AI-generated test cases must also be version-controlled and traceable — changes to AI-generated artifacts must follow formal change control procedures, and audit logs must capture when AI was used and by whom," and that regulated-industry test automation "needs to produce evidence that survives an audit, not just pass CI: every test traceable to a requirement, every AI-proposed change approved by a named human, every run reproducible, and data handled inside environments the organization actually controls." — [TestRail blog: "Software Testing in Regulated Industries: From Traceability to AI Governance"](https://www.testrail.com/blog/testing-regulated-industries/)
- On vendor lock-in as an enterprise concern: a 2025/2026 survey finds "81% of enterprises say they're at least a little concerned about their organization's dependency on specific AI vendors, and nearly a third (29%) say they're very concerned," with "data migration challenges (46%)" and "overdependence on a single vendor (46%)" as the top-cited risks; nearly half of enterprises now have "internal teams dedicated specifically to evaluating and managing AI vendors." Specific to testing: "Most AI testing tools hardcode one model provider. When you pick an AI testing vendor, you're also picking their model provider," creating a secondary lock-in layer. — [Zapier survey coverage](https://zapier.com/blog/ai-vendor-lock-in-survey/); [bug0.com: "AI gateway for testing: how to avoid model vendor lock-in"](https://bug0.com/blog/ai-gateway-vendor-lock-in-testing-2026)
- On CI/CD integration specifically: practitioner guidance notes "four causes account for most CI failures" when running AI-assisted/Playwright tests in pipelines: "missing browser system dependencies, slower CI hardware breaking timing assumptions, environment variables that exist locally but were never added to CI secrets, and a web server that has not finished booting when the first test runs." It further cautions that "AI-driven tests may behave less predictably than fully scripted Playwright tests," and that "ambiguous test intent can lead to unreliable results" along with "challenges with custom or non-standard UIs" that "may be difficult for AI to interpret accurately." — [BrowserStack guide: "Modern Test Automation with AI (LLM) and Playwright"](https://www.browserstack.com/guide/modern-test-automation-with-ai-and-playwright)
- On Selenium-to-Playwright migration specifically (a common precursor project before AI-tool adoption): "The hardest part of moving to Playwright isn't the rewrite, it's unlearning how your tests used to work," and "not every Selenium pattern has a clean 1:1 Playwright equivalent, as custom JavaScript execution, complex iframe chains, and browser extension testing require significant manual rework." Organizationally, "enterprise teams rarely fail a Selenium to Playwright migration because Playwright is weak — they fail because they treat the migration as a rewrite instead of an operating model change," with leaders worried about "retraining speed and productivity dips" when moving from Java-heavy Selenium teams to JS/TS-based Playwright. One named practitioner account states that when using Claude AI to automate the migration, "AI Helped 65-70%" of a real Selenium-to-Playwright framework conversion but the author explicitly advises "You Should Not Do It in One Shot," implying substantial manual cleanup was still required for the rest. — [scrolltest.medium.com: "I Migrated a Real Selenium Framework to Playwright. AI Helped 65-70%."](https://scrolltest.medium.com/i-migrated-a-real-selenium-framework-to-playwright-608cf6dc772f); [test-shift.com: "The Enterprise Blueprint for Migrating from Selenium to Playwright"](https://www.test-shift.com/posts/the-enterprise-blueprint-for-migrating-from-selenium-to-playwright/)

### Inferences
- Integration complexity, privacy/security review, skills gap, and reliability/hallucination concerns are cited as top-four barriers in essentially every enterprise-level survey found (WQR 2025-26, Gartner-adjacent coverage), suggesting these four form a fairly stable, convergent list of blockers across independent research efforts rather than being specific to one survey's framing.
- Vendor lock-in appears to be an emerging, second-order concern layered on top of the more basic integration/trust blockers — it's framed as a forward-looking risk enterprises are now building dedicated governance teams to manage, rather than a reason tools are being rejected today.

## What is the evidence on cost/latency/determinism issues from relying on LLM calls at scale in test pipelines (i.e., non-determinism introduced by the AI tooling itself)?

### Takeaway
Independent technical analyses converge on the finding that LLM-based test tooling introduces its own non-determinism and cost/latency overhead — self-healing specifically can turn a deterministic locator failure into a probabilistic one, and LLM-as-judge/evaluation patterns in testing carry real per-run dollar costs and multi-second latency that scale with suite size.

### Cited Findings
- A direct technical critique states self-healing "introduces flakiness" because it performs "non-deterministic element matching on low-confidence heals. A guess that passes on one run and picks a different element on the next is a flaky test." It also notes cost scales with usage: "every heal is an inference call" and this "scales with UI churn, which is exactly the thing that's increasing" due to AI coding agents generating more UI change churn. — [devassure.io: "Self-Healing Test Automation Treats the Wrong Disease"](https://devassure.io/blog/self-healing-test-automation-problems)
- On LLM evaluation/judge patterns used in testing pipelines generally: "LLM evaluation tests are slower -- expect 5 to 30 seconds per test case depending on judge model latency -- and carry real API costs. For GPT-4 as judge at current pricing, a 50-case suite might cost $1-3 per run." — [DEV Community: "LLMs Are Not Deterministic. And Making Them Reliable Is Expensive"](https://dev.to/marcosomma/llms-are-not-deterministic-and-making-them-reliable-is-expensive-in-both-the-bad-way-and-the-good-5bo4)
- On agentic non-determinism specifically: "LLM-based agents are non-deterministic in a stronger sense: identical task specifications submitted to the same agent under identical configuration can differ substantially in token consumption and reasoning path, with repeated executions of identical agentic coding tasks varying by up to 30x in total tokens consumed." — [ACEM: A Cost Estimation Model for Agentic Software Engineering (arXiv)](https://arxiv.org/pdf/2608.02582)
- Mitigation techniques themselves add cost: "Self-Consistency approaches reduce non-determinism but increase the number of LLM calls, which may improve response quality but requires more resources and may adversely impact cost/latency." — [GrowthBook: "How do you A/B test an LLM when outputs aren't deterministic?"](https://www.growthbook.io/insights/ab-testing-llms)
- A Ministry of Testing forum member raises the determinism/trust issue directly in a testing context: "AI is a tool with a probabilistic output, how can you trust it to verify the tests if every time it can output different results?" — [Ministry of Testing Club](https://club.ministryoftesting.com/t/ai-discussion-on-tools/74733)
- Practitioners cited in grey-literature review report: "developers quickly lose trust in systems that deliver inconsistent results for equal inputs" (attributed to practitioners at SAP in an academic grey-literature review), and note that practitioners "are still relying mainly on reruns and manual inspection to detect test flakiness" rather than trusting AI-automated detection. — [arXiv: "A Multi-Year Grey Literature Review on AI-assisted Test Automation"](https://arxiv.org/pdf/2408.06224)

### Inferences
- The non-determinism problem in AI-powered testing is two-layered: (1) the underlying application/test flakiness that AI tools claim to fix, and (2) new non-determinism introduced by the AI/LLM layer itself (variable token usage, probabilistic element matching, inconsistent judge outputs) — meaning in some deployments AI tooling may be adding a new source of flakiness rather than net-removing it.
- Cost overhead scales specifically with UI/code churn, which is a problem that compounds as organizations simultaneously adopt AI coding agents (increasing churn) and AI testing agents (whose cost scales with that same churn) — this is a structural scaling risk rather than a one-time integration cost.

### Gaps
- No vendor-disclosed, audited benchmark of actual per-test-run LLM API costs at enterprise scale (e.g., for Testim, Mabl, Katalon's AI features specifically) was found; the cost figures located are generic LLM-evaluation cost estimates, not tool-specific disclosed billing data.
- No study quantifying the net flakiness delta (i.e., "AI tooling removed X% of app-level flakiness but added Y% of AI-layer flakiness") was found — this would require dedicated empirical study not available in the sources reviewed.
